\# Chapter 4: Realization and Experimentation (Draft)



\## 4.1 Introduction

This chapter details the implementation of the AI-Native SOC Orchestrator. The system was designed to bridge the gap between AI agent security and traditional Security Operations Center (SOC) workflows. The realization phase involved setting up a virtualized SIEM environment, developing AI agents for attack simulation and detection, and integrating the output into a live Wazuh SIEM instance.



\## 4.2 Technical Environment

The development and testing were conducted on a host machine with the following specifications:

\- \*\*CPU:\*\* AMD Ryzen 5 5600H (6 cores, 12 threads)

\- \*\*RAM:\*\* 24 GB DDR4

\- \*\*GPU:\*\* NVIDIA RTX 3050 Ti (4 GB VRAM) - used for local LLM inference.

\- \*\*Host OS:\*\* Windows 11

\- \*\*Virtualization:\*\* VMware Workstation Pro 17.6.4

\- \*\*SIEM Guest OS:\*\* Amazon Linux 2023 (Wazuh 4.14.8 OVA)



\## 4.3 Implementation of AI Agents



\### 4.3.1 Red Agent (Attack Generation)

The Red Agent (`red\_agent.py`) utilizes the Ollama runtime with the `llama3.2:3b` model. It is designed to simulate adversarial attacks against the LLM itself, mapping the attacks to the MITRE ATLAS framework.

\- \*\*Coverage:\*\* 8 attacks across 4 techniques (AML.T0050, AML.T0051, AML.T0054, AML.T0057).

\- \*\*Output:\*\* Each attack generates a JSON log containing the attack ID, the malicious payload, the LLM's response, and the ground-truth label.



\### 4.3.2 Blue Agent (Detection and Scoring)

The Blue Agent (`blue\_agent.py`) acts as the defensive layer. It ingests the JSON logs generated by the Red Agent and applies regular expression patterns to detect prompt injection and jailbreak attempts.

\- \*\*Logic:\*\* It calculates a risk score based on whether the LLM refused the prompt (SUSPICIOUS, 65/100) or complied/leaked information (MALICIOUS, 90/100).

\- \*\*Performance:\*\* In the test campaign, the Blue Agent achieved a 100% detection accuracy (correctly classifying all 8 attacks against ground truth).



\### 4.3.3 Risk Engine (Threat Intelligence)

The Risk Engine (`risk\_engine.py`) enriches the detected IOCs. It uses `requests` to query three free Threat Intelligence APIs: AlienVault OTX, AbuseIPDB, and VirusTotal.

\- \*\*IOC Classification:\*\* It validates the IOC type (IP, hash, URL, domain) before querying, ensuring invalid data is not sent to external APIs.

\- \*\*Output:\*\* A composite Threat Intel score (0-100).



\## 4.4 SIEM Integration (Wazuh)



\### 4.4.1 Wazuh Deployment

The Wazuh OVA (v4.14.8) was imported into VMware. A critical compatibility fix was applied to the `.vmx` file to resolve CPU instruction issues on AMD Ryzen processors (`cpuid` flags and `featureCompat.enable = FALSE`).



\### 4.4.2 Indexer Connector

The `wazuh\_indexer\_connector.py` script bypasses the Wazuh Manager API and writes directly to the Wazuh Indexer (OpenSearch) on port 9200.

\- \*\*Verification:\*\* All 8 alerts were successfully ingested into the `wazuh-alerts-4.x-\*` index and verified via the Wazuh Discover tab.



\### 4.4.3 API Connector (Limitation)

The `wazuh\_api\_connector.py` script successfully authenticated with the Wazuh REST API on port 55000. However, the Wazuh Manager dropped the custom JSON events because they did not match native decoder rules. This integration is documented as a limitation and a future work item (requires custom `local\_decoder.xml`).



\## 4.5 Campaign Execution (End-to-End)

The pipeline was executed from the Windows host. The total execution time was approximately 37 seconds.

1\.  \*\*Red Agent:\*\* Generated 8 attacks and logged them to JSON.

2\.  \*\*Blue Agent:\*\* Detected the attacks, assigned risk scores, and calculated 100% accuracy.

3\.  \*\*Risk Engine:\*\* Enriched the IOCs via Threat Intel APIs.

4\.  \*\*Indexer Connector:\*\* Pushed the alerts to the Wazuh Indexer.

5\.  \*\*Reporting Engine:\*\* Generated a PDF report of the campaign.

6\.  \*\*Streamlit Dashboard:\*\* Updated in real-time to show the SIEM integration status and attack breakdown.
